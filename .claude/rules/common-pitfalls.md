# Common Pitfalls

Stack-specific traps for this Hydrogen storefront. Check these before opening a PR.

## Never put GraphQL or fetching in a component

Data is fetched in loaders/actions and passed down as typed props. A component that reads `storefrontClientContext` or defines a `gql()` document is in the wrong layer (and would ship the document to the browser) — see [module-boundaries.md](module-boundaries.md). The cart is the one client-owned dataset: read it with `useCart`, never a loader promise.

## Handle nullable Storefront fields

The Storefront API makes most fields nullable, and `noUncheckedIndexedAccess` is on. Don't assume presence.

```ts
// ❌ BAD — image / first node may be undefined
const url = product.featuredImage.url;
const first = collection.products.nodes[0].title;

// ✅ GOOD
const url = product.featuredImage?.url;
const first = collection.products.nodes[0]?.title;
```

## Don't expose private tokens to the browser

`PUBLIC_*` env vars are safe client-side; `PRIVATE_STOREFRONT_API_TOKEN` is **server-only**. Never reference it in component code or pass it through loader return data.

## Avoid request waterfalls

Independent queries in a loader run in parallel; sequential `await`s serialize them.

```ts
// ❌ BAD — sequential
const product = await storefront.graphql(PRODUCT_QUERY, ...);
const recommended = await storefront.graphql(RECOMMENDED_QUERY, ...);

// ✅ GOOD — parallel
const [productResult, recommendedResult] = await Promise.all([
  storefront.graphql(PRODUCT_QUERY, ...),
  storefront.graphql(RECOMMENDED_QUERY, ...),
]);
```

## Defer below-the-fold data — and guard it

Critical (above-the-fold) data is `await`ed; below-the-fold data is returned as a promise and rendered with `<Suspense>`/`<Await>`. Deferred queries go through `deferQuery` (`lib/http.ts`), which logs and resolves to null so a failure doesn't 500 the page.

```ts
const recommended = deferQuery(
  storefront.graphql(RECOMMENDED_QUERY, { ..., cache: Cache.long() }).then(({ data }) => data)
);
```

## Every Storefront read needs an explicit `cache`

Hydrogen 2026.10 has no implicit default: `graphql()` without a `cache` strategy hits the API on every request. Pass `Cache.long()` or `Cache.short()` per the table in [graphql-fragments.md](graphql-fragments.md). `hydrogen gql check` (inside `pnpm type-check`) validates the documents themselves; a stale schema environment is regenerated by the TypeScript plugin on the next check.

## The root middleware has two silent failure modes

`handleShopifyRoutes` and `handleShopifyRedirects` must receive `routeTemplates` (handler-owned URLs and redirect targets come out wrong without it), and `requestContext.applyResponseHeaders(response.headers)` must run on every app response (Shopify's cookies and cache headers vanish without it — consent stops loading, checkout continuity breaks). Neither throws. If `GET /api/cart` returns the app's 404 page, the middleware isn't running at all.

## CSP, the nonce and analytics are app-owned

`lib/csp.ts` builds the header and `entry.server.tsx` sets the per-request nonce on React Router's `<Scripts>` and `<ShopifyScripts nonce>`. A dropped nonce leaves pages rendering while hydration (cart, size picker, analytics) is silently dead — check the browser console for CSP violations after touching either. Analytics destinations (Shopify's, PostHog, the Meta Pixel) receive events only once Customer Privacy allows: a destination with no events in a consent-required region is working as designed, not broken. The Meta Pixel adds two of its own: `fbevents.js` is injected lazily from the first delivered event (never from `setup()`), and Meta's script enforces the pixel's Traffic Permissions allow-list — on a domain that isn't listed (localhost, an unlisted preview) it logs a warning and sends nothing, which is configuration, not a bug (docs/META_PIXEL_TESTING.md §0).

## Images through `common/Image`, prices through `common/Price`

Render Storefront and Shopify Files images with the repo's `common/Image` (`<Image data sizes />`, `sizes` presets in `lib/imageSizes.ts`) and every money value with `common/Price` (`brand` / `compact` / `cart` formats) — never a bare `<img>`, never hand-formatted currency. `common/Image.test.tsx` pins the rendered `srcset`/`sizes`/inline-style contract. Two things about `Image` that bite: it writes an inline `width` + `aspect-ratio` (from the source dimensions) that **beats any `aspect-*` or `w-*` utility** on the call site — narrow a box with the `width="75%"` prop, and know that `aspect-square` on a 4:5 product image is dead; and a `src` image given a numeric `width`/`height` switches to _fixed_ mode (1x/2x/3x at that size, full resolution), while `data` images are _fluid_ (width-descriptor ladder + `sizes`).

The image rule is not just a bandwidth nicety. A bare `<img>` pointing at a full-size CDN file makes every visitor's browser shrink a 20-megapixel photo to a card, and the GPU path browsers use for that aliases fine, regular textures (the knit on the quarter-zip) into visible wave bands. Re-uploading at a different size does not fix it; the only fix is an image delivered at the slot's own pixel size, which `<Image>` with `sizes` (and `aspectRatio` + `crop` for a cropped slot) does. Metafield JSON that carries plain URLs (`product_details`) still goes through `<Image src=...>`, not `<img>`.

## The "color = separate product" data model

The 9 live products are **separate Shopify products per color**, not variants. The color family (names, hexes, sibling links) lives in Shopify product metafields (`custom.color_*`), read via `lib/product/colors.ts`. Don't assume color is a `ProductVariant` selectedOption, and don't hardcode color/handle maps in the app.

## Tailwind traps that silently lose a style

Three bit us during the live-parity work; all three type-check and lint clean.

**`text-*` also sets `line-height`.** So a `leading-` on a shared component is overridden by any size utility a caller passes. Repeat the leading next to each size:

```tsx
// ❌ variant's leading-[1.1] is dead — text-4xl re-sets line-height
<Heading className="text-4xl" />
// ✅
<Heading className="text-4xl leading-[1.1]" />
```

**Live's Impulse breakpoints have named tokens.** The live theme flips at 769/1025 (one past Tailwind's `md`/`lg`) — use `impulse:` / `impulse-lg:` (defined in tailwind.css `@theme`) for surfaces that must flip exactly where live does. Named breakpoints sort by width, so they interleave correctly with `md`/`lg`/`xl`. The one holdout is `routes/products.$handle.tsx`, which keeps arbitrary `min-[769px]:` variants on purpose — its chains rely on named-beats-arbitrary emit order (see the next trap) and need visual re-verification to move.

**Named and arbitrary breakpoints don't interleave.** Tailwind emits named variants (`md:`) after arbitrary ones (`min-[1440px]:`), so the named one wins at the larger width regardless of intent. Use one form or the other in a chain:

```tsx
// ❌ md:px-5 still applies at 1440
<div className="px-3 md:px-5 min-[1440px]:px-0" />
// ✅ sorts by width
<div className="px-3 min-[768px]:px-5 min-[1440px]:px-0" />
```

**A preset `size` on `Heading`/`SectionHeader` carries responsive steps** (`md:`/`xl:`) that a `className` can't override at those breakpoints. Pass `size="none"` when a page owns its whole scale.

**`aspect-*` plus `min-h-*` on an auto-width box widens the box, not just its height.** CSS transfers a min/max constraint through `aspect-ratio` into the other axis whenever that axis is `auto`, so `min-h-[50rem] aspect-[2400/1543]` on a full-bleed section becomes a 1244px _min-width_ and the page scrolls sideways on every narrower viewport. Give the box an explicit width (`w-full`) so there is nothing to transfer; `min-w-0` does not help. Measure `document.documentElement.scrollWidth` against `clientWidth` after any aspect-ratio change.

## The base layer caps every `form` at 400px

`app/styles/tailwind.css` has `form { max-width: 400px }` from `md` up (a Hydrogen skeleton leftover). Any full-width form control — the PDP add-to-cart bar, a sticky bar — needs to opt out (`[&>form]:max-w-none` on a wrapper). Check rendered width, not just the classes on the button.

The same skeleton block also styles every bare `input` (`margin-top: 0.25rem`, `margin-bottom: 0.5rem`, border, radius, padding). Utility classes on the input override the ones you set — but any you _don't_ set leak through: a custom-styled input needs `m-0` (and `rounded-none` if square) or it sits 4px lower than the button beside it. Measure the rendered row, not the classes.

## Server packages must have a workerd build

Oxygen and MiniOxygen run on workerd, not Node. A package whose default entry imports Node built-ins (`path`, `fs`, `process.cwd()`) fails at load with an opaque `MiniOxygen couldn't load your app's entry point` error. `posthog-node` is the known case, so import it from **`posthog-node/edge`**. Its edge build has no AsyncLocalStorage, so `withContext()` does nothing there. [lib/analytics/posthog.server.ts](../../app/lib/analytics/posthog.server.ts) attaches the visitor through `before_send` instead.

## Runtime config beats `VITE_*`

`import.meta.env.VITE_*` is inlined at **build** time, so every Oxygen environment gets the same value. Anything that differs between Production and Preview (like the PostHog project key) is a `PUBLIC_*` Oxygen var, read from `context.env` and passed to the client through the root loader.

## No `any`

`no-explicit-any` is a warning we treat as a defect — it hides type mismatches. Use `unknown` + narrowing, generics, or the generated types instead.

## Don't edit generated files

`.react-router/types/*` (route typegen) and the root `*-graphql-env.d.ts` files (the Hydrogen ts-plugin's schema environments, gitignored) are regenerated — never edit them.

## Hydrogen is a library now — don't reach for the classic framework APIs

Since [ADR 0010](../../docs/decisions/0010-hydrogen-2026-10-library.md) the repo runs Hydrogen 2026.10 (`^2026.10`). `createHydrogenContext`, `hydrogenRoutes`, `hydrogenPreset`, `CartForm`, `useOptimisticCart`, `Analytics.Provider`, `<Image>`, `<Money>`, `<Pagination>`, `getSitemap*`, `storefrontRedirect` and `createContentSecurityPolicy` no longer exist; the packaged skills under `.claude/skills/hydrogen-*` are the version-correct reference (resync with `hydrogen skills sync` after a bump; `skills check` runs in CI, so never hand-edit or reformat them).
